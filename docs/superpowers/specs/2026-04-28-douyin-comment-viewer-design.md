# 抖音评论查看页设计

## 背景

当前项目的目标已经从泛平台内容抓取，逐步收敛到“围绕评论进行查看、监控和后续线索发现”。但现阶段 WebUI 中虽然存在数据中心和预览逻辑，评论数据仍然无法稳定查看，原因主要有两点：

1. 当前主流程稳定落地的数据仍以 `normalized` 内容记录为主，评论标准化结果没有正式成为主要展示对象。
2. 现有 `DataExplorer` 评论预览逻辑依赖旧式评论字段，和当前后端能稳定提供的数据结构并不一致。

因此，第一步不直接做完整的评论监控台或线索识别，而是先补齐“抖音评论可视化查看能力”，让用户能在界面中查看、筛选、点开和回看评论详情。

## 目标

本次设计仅面向抖音，目标如下：

- 在现有 WebUI 中新增一个专门的“评论查看页”
- 只接入抖音评论数据，不处理其他平台
- 支持从现有数据目录中发现可查看的抖音评论来源
- 支持评论列表分页浏览
- 支持关键词搜索、评论层级筛选、地区/IP 属地筛选
- 支持查看单条评论详情和原始 payload
- 为后续演进到“单作品监控项 + 评论流 + 运行日志”的桌面版保留结构延展性

## 非目标

本阶段明确不做以下内容：

- 不做自动线索识别
- 不做监控项持续刷新调度
- 不做评论处理状态流转
- 不做桌面壳打包
- 不做多平台统一评论查看
- 不强行重构现有全部数据中心页面

## 推荐方案

推荐方案是在现有 React WebUI 内新增独立的“评论查看页”，后端增加面向抖音评论的专用只读接口，而不是继续把评论展示逻辑塞进通用文件预览器。

推荐原因：

- 改动路径最短：复用现有 `FastAPI + React` 架构
- 语义更清晰：评论查看页就是业务界面，不再把评论展示伪装成文件预览
- 后续兼容桌面版：未来左侧“评论来源列表”可以平滑替换为“监控项列表”
- 不阻塞后续线索层：评论事实层和线索层可以自然分离

## 备选方案

### 方案 A：新增评论查看页（推荐）

在现有导航中新增“评论查看”页，后端新增抖音评论只读接口。

优点：

- 结构最清晰
- 后续最容易演进成桌面监控台
- 评论字段、筛选项和详情面板可按业务直接设计

缺点：

- 需要新增一组接口和一个页面

### 方案 B：继续复用数据中心页面

在 `DataExplorer` 内增强评论预览逻辑，动态适配抖音评论结构。

优点：

- 前期代码改动较少

缺点：

- 文件浏览与评论工作台语义混杂
- 后续扩展监控项、日志和线索侧栏时容易变形

### 方案 C：只增强原始 JSONL 文件预览

先不做评论业务界面，只把评论 JSON 直接更好地展示出来。

优点：

- 开发最快

缺点：

- 仍然不是工作台体验
- 不适合作为后续桌面版基础

## 目标架构

本阶段采用以下结构：

- 现有抓取输出继续保留 `tasks / events / raw / normalized`
- 新增抖音评论查看接口层，负责从数据目录中定位和解析评论来源
- 新增 React 评论查看页面
- 先以“评论文件/评论来源”为左侧导航对象，不强依赖正式监控项模型

数据流如下：

1. 前端加载评论查看页
2. 请求评论来源列表
3. 用户点击某个来源
4. 前端请求评论分页列表
5. 用户使用筛选条件重新拉取列表
6. 用户点击某条评论
7. 前端请求或展示该评论详情与原始 payload

## 后端设计

### 路由

建议新增独立路由，例如：

- `GET /api/comments/sources`
- `GET /api/comments`
- `GET /api/comments/{comment_id}`

不建议把评论查看逻辑继续挂在 `/api/data/files/*` 下，因为评论查看的主语应是“评论”，不是“文件”。

### 评论来源列表接口

用于返回当前可查看的抖音评论来源。第一版来源可以仍然基于本地文件，但返回结构应是业务化对象，而不是原始文件列表。

建议返回字段：

- `source_id`
- `platform_code`
- `platform_content_id`
- `content_title`
- `content_url`
- `comment_count`
- `latest_comment_at`
- `updated_at`
- `file_path`

第一版允许 `content_title` 缺失，如果评论文件中没有足够上下文，可先退化为作品 ID。

### 评论列表接口

用于分页返回某个评论来源下的评论。

建议查询参数：

- `source_id`
- `keyword`
- `comment_level`
- `location`
- `limit`
- `offset`
- `sort`

建议返回字段：

- `items`
- `total`
- `limit`
- `offset`

单条评论建议统一返回这些字段：

- `comment_id`
- `platform_comment_id`
- `platform_content_id`
- `parent_comment_id`
- `root_comment_id`
- `comment_level`
- `comment_text`
- `author_platform_id`
- `author_nickname`
- `author_avatar`
- `ip_location`
- `author_home_location`
- `published_at`
- `like_count`
- `reply_count`
- `raw_payload_available`

第一版如果部分字段暂时缺失，接口也应稳定返回空字符串或 `null`，不要让前端自行猜结构。

### 评论详情接口

用于查看单条评论的完整信息。

建议返回：

- 评论列表接口中的全部字段
- `metadata`
- `raw_payload`
- `first_seen_run_id`
- `last_seen_run_id`

即使当前尚未引入 run 体系，也可以先返回空值，以保证未来接口形状稳定。

### 解析与适配层

第一版很可能面对“评论文件结构不完全统一”的现实，因此后端应包含一个轻量适配层，负责把现有抖音评论数据映射成统一视图模型。

适配层职责：

- 识别抖音评论文件
- 读取 JSON / JSONL / 预览数据
- 将旧字段映射为统一评论字段
- 兜底空字段和异常字段
- 负责简单过滤、搜索和排序

这样前端可以只面对统一结构，不再依赖历史文件格式。

## 前端设计

### 页面位置

在现有侧边导航中新增一个单独入口，例如“评论查看”。

不建议直接替换“数据中心”，因为数据中心仍然保留通用文件浏览价值。

### 页面结构

页面分为三块：

1. 左侧评论来源列表
2. 中间评论表格
3. 右侧或弹层评论详情

布局目标是贴近后续桌面监控台，但不强行在第一版加入运行日志和监控控制。

### 左侧评论来源列表

每个来源卡片显示：

- 作品标题或作品 ID
- 评论总数
- 最近更新时间
- 平台标识（固定为抖音）

支持按标题或作品 ID 搜索来源。

### 中间评论表格

第一版建议列如下：

- 评论时间
- 评论内容
- 昵称
- 用户 ID
- IP 属地 / 地区
- 评论层级
- 回复对象
- 点赞数

列表要求：

- 支持关键词搜索
- 支持只看一级评论 / 二级回复
- 支持地区过滤
- 默认按时间倒序
- 支持分页

### 评论详情面板

点击评论后显示：

- 完整评论文本
- 评论人信息
- 评论层级和回复关系
- 所属作品 ID
- 发布时间
- 地区/IP 属地
- 原始 payload
- metadata

详情视图必须支持长文本与 JSON 折叠显示，避免界面挤压。

## 数据模型边界

虽然本阶段主要做可视化，但为了后续线索发现，评论视图模型需要从一开始就按“评论事实层”定义，而不是只取几个临时展示字段。

建议事实字段至少包含：

- 评论主键
- 作品主键
- 父评论关系
- 根评论关系
- 评论层级
- 评论正文
- 用户标识
- 用户昵称
- 用户头像
- 位置字段
- 时间字段
- 互动字段
- 原始 payload
- metadata

后续线索层再另起 `comment_leads`，不和事实评论表混存。

## 错误处理

后端应处理并显式返回以下场景：

- 找不到评论来源
- 评论文件为空
- 评论文件格式错误
- 评论列表解析失败
- 请求参数非法

前端对应空状态：

- 没有评论来源时显示引导文案
- 某来源无评论时显示空表状态
- 接口失败时显示错误提示与重试按钮

禁止出现白屏或静默失败。

## 测试与验收

完成后应至少验证以下场景：

1. 页面能展示抖音评论来源列表
2. 选择来源后能看到评论分页列表
3. 关键词搜索可以过滤评论
4. 可以区分一级评论和二级回复
5. 可以看到地区/IP 属地字段
6. 点击评论可以看到完整详情与原始 payload
7. 无数据、坏数据、字段缺失时界面仍然可用

## 实施建议

实施顺序建议如下：

1. 明确并实现后端统一评论视图模型
2. 新增评论来源列表接口
3. 新增评论分页与详情接口
4. 新建 React 评论查看页
5. 接入筛选、分页与详情面板
6. 用现有抖音评论数据进行联调和空状态验证

## 后续演进

本设计完成后，可以自然扩展到下一阶段：

- 左侧从评论来源切换为正式监控项
- 下方增加运行日志
- 接入持续刷新任务
- 接入评论标准化持久层
- 接入线索识别与处理状态
- 最终封装为桌面版

## 结论

当前最合适的切入点不是先做完整监控器，而是先在现有项目里新增一个只面向抖音的评论查看页，打通“评论来源发现、评论列表浏览、评论详情回看”这三件事。这样既能尽快解决“评论数据看不了”的问题，也能为后续桌面版评论监控台与线索发现系统打下稳定基础。
